# adder

[![CI](https://github.com/TyphonHill/adder/actions/workflows/ci.yml/badge.svg)](https://github.com/TyphonHill/adder/actions/workflows/ci.yml)
[![Go Reference](https://pkg.go.dev/badge/github.com/TyphonHill/adder.svg)](https://pkg.go.dev/github.com/TyphonHill/adder)
[![License](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)

Write the pattern once. adder adds the rest.

adder generates and maintains the repeated pieces of a Go repository: the registries, wiring, and boilerplate that follow from conventions your team already has. You describe them once in `adder.yaml` with ordinary Go templates, and adder keeps them in step with your code.

> **Status:** early development. `adder derive`, `adder check`, and `adder new` work today; the configuration format may still change before v1.0.0.

## How it works

`adder derive` runs in two steps:

1. **Scan.** adder parses the Go files in the directories you name and collects the functions and methods that match your filters, such as "exported and named `New`". It only reads the source; nothing is compiled or run.
2. **Render.** Each list of matches is passed to your templates under the name you gave it, and adder writes the result.

Change your code, run `adder derive` again, and the generated files follow.

`adder new` creates the code people then own, such as a new driver package, from [generators](#generators) with validated inputs. It updates the derived files in the same run, so the new driver is registered as soon as it exists.

## Install

adder supports the two most recent Go releases (currently Go 1.26 and later). Add it as a tool dependency of your module:

```sh
go get -tool github.com/TyphonHill/adder/cmd/adder
go tool adder --help
```

Or install the binary:

```sh
go install github.com/TyphonHill/adder/cmd/adder@latest
```

## Quick start

Say your storage library has one package per driver under `drivers/`, and each exports a `New` constructor:

```
drivers/
  local/local.go   // func New(config map[string]string) (driver.Driver, error)
  s3/s3.go         // func New(config map[string]string) (driver.Driver, error)
```

Instead of keeping a list of drivers up to date by hand, tell adder where to find them. This `adder.yaml` at the repository root defines a scan named `Drivers`, which collects every exported function named `New` in the packages under `drivers/`, and an output that renders a template with that list:

```yaml
version: 1
derive:
  scans:
    Drivers:
      dirs: ["drivers/*"]
      funcs:
        exported: true
        name: ^New$
  outputs:
    - template: templates/drivers.go.tmpl
      path: drivers/drivers.gen.go
```

The template reads the matches through `.Drivers`, the name of the scan. Each match has fields such as `.Name`, `.Package`, and `.ImportPath`:

```gotemplate
package drivers

import (
	"{{ .Module }}/driver"
{{- range .Drivers }}
	"{{ .ImportPath }}"
{{- end }}
)

// All maps each driver name to its constructor.
var All = map[string]driver.Factory{
{{- range .Drivers }}
	"{{ .Package }}": {{ .Package }}.New,
{{- end }}
}
```

Then run:

```sh
$ go tool adder derive
created    drivers/drivers.gen.go
```

```go
// Code generated by adder from templates/drivers.go.tmpl. DO NOT EDIT.

package drivers

import (
	"example.com/storage/driver"
	"example.com/storage/drivers/local"
	"example.com/storage/drivers/s3"
)

// All maps each driver name to its constructor.
var All = map[string]driver.Factory{
	"local": local.New,
	"s3":    s3.New,
}
```

Running it again leaves the file alone and prints nothing, or `unchanged` with `--verbose`. Add a `drivers/gcs` package and the registry follows. This example is the test fixture in [`internal/derive/testdata/basic`](internal/derive/testdata/basic).

## Commands

| Command | Description |
| --- | --- |
| `adder init` | Write a starter `adder.yaml` with commented examples of each section. |
| `adder derive` | Run every scan and rewrite the derived outputs that changed. |
| `adder check` | Report derived outputs that are out of date, without writing anything. Exits with status 3 when any are, so CI can catch a forgotten `adder derive`. |
| `adder new <generator>` | Create files with a generator, then update the derived outputs. `adder new` lists the generators, and `adder new <generator> --help` shows its inputs. |
| `adder list` | List the generators and derived outputs in `adder.yaml`. |
| `adder describe <generator>` | Show a generator's inputs, with the values its scans allow now, and the files it creates. With `--json`, it includes a JSON Schema of its inputs. |
| `adder explain <file>` | Show which output and template produced a file, the scans the template uses, and whether the file is up to date. |
| `adder test [generator...]` | Run the generators' tests and compare the files they create with golden files. `--update` rewrites the golden files. |

Global flags:

| Flag | Default | Description |
| --- | --- | --- |
| `--root` | the directory holding `adder.yaml` | Repository root that scans and outputs are relative to. |
| `-c`, `--config` | `<root>/adder.yaml` | Configuration file. Template paths resolve against its directory. |
| `--json` | off | Print the result and any problems as one JSON object on standard output. See [JSON output](#json-output). |
| `-q`, `--quiet` | off | Print only problems, and diffs asked for with `--diff`. |
| `-v`, `--verbose` | off | Also print unchanged files and, for `derive` and `check`, how many items each scan found. |

Without either flag, adder finds `adder.yaml` in the current directory or the nearest parent that has one, the way `go` finds `go.mod`, so commands work from anywhere in the repository. With only `--config`, the root is that file's directory.

In a terminal, statuses and problem codes are in color. Set `NO_COLOR` to turn color off; it is also off when output is not a terminal, when `TERM` is `dumb`, and with `--json`.

`adder completion bash`, `zsh`, `fish`, or `powershell` prints a completion script, which completes generator names, each generator's flags, input values from `values` and `valuesFrom`, and generated files for `adder explain`. For zsh, for example, run `adder completion zsh > "${fpath[1]}/_adder"`; `adder completion <shell> --help` explains each shell.

`derive` flags:

| Flag | Description |
| --- | --- |
| `-n`, `--dry-run` | Show what would change without writing anything. |
| `--diff` | Also show each change as a unified diff, without writing anything. |
| `--out <dir>` | Write outputs under another directory instead of the root. |

`check` flags:

| Flag | Description |
| --- | --- |
| `--diff` | Also show each out-of-date output as a unified diff, so a CI log says exactly what is stale. |

`new <generator>` flags, besides one for each input:

| Flag | Description |
| --- | --- |
| `-n`, `--dry-run` | Show what would change without writing anything. |
| `--diff` | Also show each change as a unified diff, without writing anything. The output is a patch that `git apply` accepts. |
| `--inputs <file>` | Read inputs from a JSON object keyed by input name, such as `{"name": "gcs", "cache": true}`. Use `-` for standard input. Flags override it. |

### Errors and exit codes

Problems are reported with their location and a stable code, and adder reports every problem it finds rather than stopping at the first:

```
templates/drivers.go.tmpl:12:4: <.Drivrs>: map has no entry for key "Drivrs" [template-exec]
	hint: available fields: Drivers, Module, Vars
```

| Exit code | Meaning |
| --- | --- |
| `0` | Success. |
| `1` | adder ran and found a problem. |
| `2` | adder was invoked incorrectly, such as an unknown flag or a missing generator input. |
| `3` | `adder check` found outputs that are out of date. |

See [docs/design.md](docs/design.md#4-structured-diagnostics) for the full list of codes.

### JSON output

With `--json`, every command prints exactly one JSON object on standard output and nothing on standard error, whether it succeeds or fails. Exit codes are the same as without it, so scripts and coding agents can drive adder without parsing text. For the [driver generator](#generators) below:

```console
$ adder new driver --name gcs --dry-run --json
{
  "generator": "driver",
  "dryRun": true,
  "changes": [
    {"path": "drivers/gcs/gcs.go", "status": "created"},
    {"path": "drivers/drivers.gen.go", "status": "updated"}
  ],
  "message": "Next, implement New in drivers/gcs/gcs.go.",
  "problems": []
}
```

| Command | Fields |
| --- | --- |
| `derive` | `dryRun`, `changes`, `problems` |
| `check` | `changes`, `problems` |
| `new <generator>` | `generator`, `dryRun`, `changes`, `message`, `problems` |
| `init` | `changes`, `problems` |
| `list` | `generators`, `outputs`, `problems` |
| `describe <generator>` | `name`, `description`, `inputs`, `files`, `message`, `derive`, `inputSchema`, `problems` |
| `explain <file>` | `path`, `generated`, `template`, `output`, `scans`, `status`, `problems` |
| `test` | `tests`, each with `generator`, `name`, `passed`, and `changes`, then `problems` |

- `changes` lists every file in the plan, unchanged ones included. Each has a `path`, relative to the root with forward slashes, and a `status`: `unchanged`, `created`, `updated`, `skipped`, or `removed`. With `--diff`, changes that write or remove a file also have a `diff`.
- `problems` is always present and empty on success. Each problem has a `code`, a `message`, and, when known, a `pos` with `file`, `line`, and `column`, and a `hint`. Invocation mistakes, such as an unknown flag, have the code `usage`.
- `adder check` reports stale outputs as changes, not problems, and exits with status 3.
- `--help` still prints text.
- `describe`'s `inputSchema` is a JSON Schema (draft 2020-12) for the object `adder new --inputs` accepts, the shape MCP uses for tool inputs. `unique` becomes `"not": {"enum": [...]}` listing the values that exist now, and `valuesFrom` becomes `enum`.

A coding agent can discover and run any generator this way: `adder list --json`, then `adder describe <generator> --json`, then `adder new <generator> --inputs - --dry-run --json` to preview, then the same without `--dry-run`.

## Configuration

### Scans

Each entry under `derive.scans` selects declarations: functions and methods by default, type declarations with a `types` block, or constants and variables with a `values` block. A scan can also list files that are not Go source with a `files` block. A scan uses one of `funcs`, `types`, `values`, and `files`. Its name becomes the template field that holds the results, so it must be a valid Go identifier other than `Module`, `Vars`, `Inputs`, or `Item`, which adder provides.

| Field | Description |
| --- | --- |
| `dirs` | Directories to scan, relative to the repository root and written with forward slashes. Glob patterns such as `drivers/*` are allowed, and `**` matches any number of directories, as in `internal/**/handlers`. Like `go`'s `./...`, wildcards skip `testdata`, `vendor`, and directories starting with `.` or `_`. Files adder generated are never scanned. |
| `exclude` | Directories to leave out, in the same syntax as `dirs`. `internal/legacy/**` excludes a directory and everything below it. |
| `includeTests` | Also scan `_test.go` files. Defaults to `false`. |
| `buildTags` | Custom build tags to treat as set, such as `[integration]`. |
| `funcs.exported` | Only match exported names. |
| `funcs.name` | Only match names containing a match for this regular expression. |
| `funcs.kind` | `func` for plain functions only, or `method` for methods only. |
| `funcs.receiver` | Only match methods on this type, with a value or pointer receiver. |
| `funcs.firstParam` | Only match declarations whose first parameter has this name. |
| `funcs.firstParamType` | Only match declarations whose first parameter has this type, written as Go writes it but with full import paths: `context.Context`, `go.temporal.io/sdk/workflow.Context`, `*Config`. |
| `funcs.directive` | Only match declarations with this [directive](#directives) in their doc comment. |
| `types.exported` | Only match exported type names. |
| `types.name` | Only match type names containing a match for this regular expression. |
| `types.kind` | `struct`, `interface`, or `type` for any other type declaration. |
| `types.directive` | Only match types with this [directive](#directives) in their doc comment. |
| `values.kind` | `const` or `var`. |
| `values.exported` | Only match exported names. |
| `values.name` | Regular expression the name must match. |
| `values.type` | The type as written, such as `Color`. In a `const` group, a name without its own type and value repeats the one before it, as Go does, so every member of an `iota` enum has its type. |
| `values.directive` | Only match names with this directive, in their own doc comment or in their group's. A name's own directive replaces the group's directive of the same name. |
| `typeCheck` | Load type information, for the filters below that compare types. Runs the `go` command offline; see [type-aware scans](#type-aware-scans). |
| `platform` | With `typeCheck`, the `GOOS/GOARCH` to check, such as `windows/arm64`. Defaults to `linux/amd64`. |
| `types.implements` | With `typeCheck`, only types whose values or pointers implement this interface, written with its import path, such as `io.Writer` or `example.com/m/driver.Driver`, or `error`. Interfaces and generic types are never selected. |
| `files.name` | Regular expression the file name, with its extension, must match, such as `^[0-9]+_.*\.sql$` for migrations. Without it, every file is listed. Hidden files, symbolic links, and files adder generated are skipped, and contents are not read. |

Files that no platform can build are skipped, such as those marked `//go:build ignore` or with a custom tag that `buildTags` does not list. Platform tags such as `linux` or `amd64` may take any value, so results are the same on every machine, and file name suffixes such as `_windows.go` never exclude a file.

Every match is an item with these fields, sorted by name:

| Field | Description |
| --- | --- |
| `.Name` | Declared name, or for file scans the file name. |
| `.Kind` | `func`, `method`, `struct`, `interface`, `type`, `const`, `var`, or `file`. |
| `.Receiver` | Receiver type for methods, empty for functions. |
| `.Package` | Package name from the file's `package` clause. |
| `.ImportPath` | The package's import path, empty when the repository has no `go.mod`. |
| `.Dir` | Directory relative to the root. |
| `.File` | File path relative to the root. |
| `.Line` | Line of the declaration. |
| `.Doc` | Doc comment, without directives. |
| `.Signature` | For functions, parameters and results as written, such as `(ctx context.Context) error`. |
| `.Params`, `.Results` | For functions, each parameter and result, with `.Name` and `.Type` as written. |
| `.Fields` | For structs, each field with `.Name`, `.Type`, `.Tag`, and `.Embedded`. |
| `.Type` | For constants and variables, the type as written, repeated through a `const` group. |
| `.Value` | For constants and variables, the value as written. Empty for a constant that repeats the one before it, and when several names share one value, as in `a, b = f()`. |
| `.Iota` | For constants, the position in their `const` group, which is their value of `iota`. |
| `.Pointer` | For types selected by `implements`, true when only a pointer to the type implements the interface, so a registry can write `&{{ .Name }}{}`. |
| `.Directives` | The arguments of each [directive](#directives), by directive name. |

Fields that do not apply to a declaration are empty.

### Type-aware scans

A scan with `typeCheck: true` loads the scanned packages' types with the Go toolchain, so filters compare types rather than how they are written:

```yaml
scans:
  Drivers:
    dirs: ["drivers/*"]
    typeCheck: true
    types: {implements: example.com/store/driver.Driver}
```

```gotemplate
var All = []driver.Driver{
{{- range .Drivers }}
	{{ if .Pointer }}&{{ end }}{{ .Package }}.{{ .Name }}{},
{{- end }}
}
```

- `implements` selects every type that implements the interface, whatever it is called.
- `funcs.firstParamType` matches through import aliases, dot imports, and type aliases.
- `values.type` matches a constant's or variable's type, even when it is inferred, as in `const Red = Color(1)`. A type in the scanned package can be written without its import path.

Type-aware scans are slower than parsing, and need the `go` command on `PATH`, code that compiles, and its dependencies already downloaded: adder never downloads anything, and reports a missing dependency as a `type-check` problem. Every run checks the same platform, `linux/amd64` unless `platform` says otherwise, with cgo off and nothing from your environment that changes which files are built, so output is the same on every machine. `adder new` type checks the files it is about to create, so registries pick up a new type in the same run.

### Directives

Code can opt in to a scan explicitly with a directive in its doc comment, instead of relying on naming conventions:

```go
// S3 stores objects in a bucket.
//
//adder:register name=s3 desc="Amazon S3"
type S3 struct{}
```

Directives follow Go's convention for tool directives, like `//go:generate`: no space after `//`, then `adder:` and a lowercase name. Arguments are `key=value` pairs, and values with spaces are written as Go strings. A scan with `directive: register` selects only declarations that have it, and templates read the arguments from `.Directives`:

```gotemplate
{{ range .Storage }}{{ index .Directives.register "desc" }}{{ end }}
```

When a directive is optional, use `index` to look it up, which returns nothing instead of failing: `{{ with index .Directives "register" }}...{{ end }}`.

### Outputs

Each entry under `derive.outputs` renders one `template` to one `path`. Template paths are relative to the directory holding `adder.yaml`, and output paths are relative to the repository root. Both use forward slashes and must stay inside their root. Nothing is written unless every output renders.

Go outputs are formatted with `gofmt`, lose the imports they never use, and are marked as generated with Go's [standard header](https://go.dev/s/generatedcode), so editors, linters, and code review tools treat them as generated:

```go
// Code generated by adder from templates/drivers.go.tmpl. DO NOT EDIT.
```

adder adds its header even when a template writes another tool's `// Code generated ... DO NOT EDIT.` line, since that is how adder tells its own files apart: scans skip them, and stale ones are removed. A template that writes adder's exact header keeps it.

adder never replaces a file it did not generate. When a file already sits at an output's path without adder's header, `derive` stops with a `file-exists` problem and writes nothing, so move or delete the file first. Outputs of a type that gets no header, such as JSON, are replaced as before, since adder cannot tell its own apart.

Outputs in other languages get the same header in their own comment syntax, chosen by file extension: `#` for YAML, TOML, Python, shell scripts, Makefiles, and Dockerfiles; `//` for TypeScript, JavaScript, Rust, Java, and Protocol Buffers; `--` for SQL; `/* */` for CSS; and `<!-- -->` for Markdown, HTML, and XML. It goes after a leading `#!` line, XML declaration, or Markdown front matter. JSON and other files without comments get no header. See [design 25](docs/design.md#25-generated-file-headers-for-other-languages) for the full table.

Because unused imports are removed, templates can import everything a file might need instead of wrapping each import in `{{ if }}`. adder recognizes a package by its explicit name or by the last element of its path, so give an import an explicit name when its package name differs from its path. Missing imports are not added ([design 21](docs/design.md#21-unused-imports-are-removed-missing-ones-are-not-added)).

Templates also receive `.Module`, the module path from the root's `go.mod`, and `.Vars`. Referencing a field that does not exist is an error, so typos fail loudly.

#### One file per item

An output with `each` renders its template once for every item of a scan, available as `.Item`, and its `path` is a template rendered for each one:

```yaml
derive:
  outputs:
    - template: templates/mock.go.tmpl
      each: Stores
      path: "{{ .Item.Dir }}/{{ .Item.Package }}_mock.gen.go"
```

- Every item must render to its own path, so the path almost always uses `.Item`.
- The template still sees every scan, `.Vars`, and `.Module`, and must not be used by another output.
- Files the output generated before but no longer produces, such as a mock for a store that was deleted, are removed. A file is only removed when its path matches the output's `path`, with each `{{ }}` matching anything, and its header names the output's template. `testdata`, `vendor`, and hidden directories are never searched, and files without adder's header are never removed.
- The path must end in a file type that gets a header, because that is how stale files are found.

`adder check` reports a file to remove as stale, `--diff` shows it as a deletion, and `adder derive` deletes it.

adder never writes or removes a file through a symbolic link: an output whose path, or a directory on it, is a link inside the root is an error. Scans skip symbolic links to files and directories.

### Vars and partials

`vars` holds strings every template can read, and `partials` lists templates whose `{{ define }}` blocks every template can use. Both sit at the top level of `adder.yaml`:

```yaml
version: 1
vars:
  Owner: Example Inc.
  License: Apache-2.0
partials:
  - templates/partials/*.tmpl
```

```gotemplate
{{/* templates/partials/license.tmpl */}}
{{ define "license" -}}
// Copyright {{ .Vars.Owner }}. Licensed under {{ .Vars.License }}.
{{ end }}
```

```gotemplate
{{/* templates/drivers.go.tmpl */}}
{{ template "license" . }}
package drivers
```

- Var names are Go identifiers, read as `.Vars.<name>`. Values are strings.
- Partial patterns are relative to the directory holding `adder.yaml` and use [`path.Match`](https://pkg.go.dev/path#Match) syntax, without `**`. Each pattern must match at least one file.
- Only the `{{ define }}` blocks in a partial are used; text outside them is ignored. Pass data along with `{{ template "name" . }}`, since a partial sees only what it is given.
- Two partials cannot define the same name. A template can redefine a partial's block for itself, which leaves other templates unaffected.

### Generators

Each entry under `generators` is a command, `adder new <name>`, that renders new files from templates. Generator names are lowercase words joined by hyphens.

```yaml
generators:
  driver:
    description: Add a storage driver
    inputs:
      name:
        help: Driver name, used as the package name
        pattern: "[a-z][a-z0-9]*"
        unique: Drivers.Package
      summary:
        help: One-line description for the package documentation
        default: stores objects
      cache:
        type: bool
        help: Add an in-memory cache in front of the driver
    files:
      - template: templates/new/driver.go.tmpl
        path: drivers/{{ .Inputs.name }}/{{ .Inputs.name }}.go
      - template: templates/new/cache.go.tmpl
        path: drivers/{{ .Inputs.name }}/cache.go
        when: cache
    message: |
      Next, implement New in drivers/{{ .Inputs.name }}/{{ .Inputs.name }}.go.
```

```console
$ adder new driver --name gcs --cache
created    drivers/gcs/gcs.go
created    drivers/gcs/cache.go
updated    drivers/drivers.gen.go

Next, implement New in drivers/gcs/gcs.go.
```

Input names are lowerCamelCase. Each one is a flag in kebab-case (`packageName` is `--package-name`) and a template field (`.Inputs.packageName`). Every problem with the inputs is reported at once, and nothing is written unless the whole run succeeds.

Run in a terminal, `adder new` asks for required inputs that were not given instead of failing, listing allowed values by number and asking again until an answer is valid. Optional inputs keep their defaults, so the result is the same as with flags. Scripts, CI, and agents, which have no terminal, get a `missing-input` problem as before, and so do `--json` and `--inputs -`.

| Input field | Description |
| --- | --- |
| `type` | `string`, the default, or `bool`. Bool inputs are `false` unless their flag is given. |
| `help` | Shown in `--help` and with problems. |
| `default` | Makes a string input optional. A string input without one is required. |
| `pattern` | A regular expression the whole value must match. |
| `values` | The allowed values. |
| `valuesFrom` | Takes the allowed values from a scan, written as `Scan.Field`, such as `Drivers.Package`. |
| `unique` | Rejects values a scan already has, written as `Scan.Field`, so two drivers cannot share a name. |

| File field | Description |
| --- | --- |
| `template` | The template, relative to the directory holding `adder.yaml`. |
| `path` | Where to create the file, relative to the root. It is a template, rendered with the same data, and must stay inside the root. |
| `when`, `unless` | Name a bool input that includes or excludes the file. |
| `ifExists` | `fail`, the default, or `skip` for files that may already exist, such as a shared README. adder never overwrites a file. |

| Generator field | Description |
| --- | --- |
| `description` | Shown in `adder new`. |
| `message` | A template printed after the files are created, such as next steps. |
| `derive` | Set to `false` to skip updating derived outputs. |
| `tests` | Sample inputs and the files the generator should create from them, for `adder test`. |

Generator templates see `.Inputs`, `.Vars`, `.Module`, and every scan. Scans see the new files before they are written, which is how derived outputs pick them up in the same run. Go files are formatted with `gofmt` but get no generated-code header, because they are meant to be edited. A complete example is the test fixture in [`internal/scaffold/testdata/drivers`](internal/scaffold/testdata/drivers).

#### Testing generators

A generator can declare tests: sample inputs, and a directory of the files it should create from them, at their paths in the repository.

```yaml
generators:
  driver:
    # inputs, files, and message as above
    tests:
      - name: with-cache
        inputs: {name: example, cache: true}
        want: testdata/generators/driver/with-cache
```

`adder test` runs each test like `--dry-run` and compares the files the generator creates with the files under `want`. A missing, extra, or different file fails the test with a diff, a `golden-mismatch` problem, and exit status 1. `adder test --update` writes what the generator creates now, so review the diff before committing it.

- `want` is relative to the directory holding `adder.yaml`. Keep it under `testdata`, which scans with `**` and Go tooling ignore.
- Derived outputs are not compared, because they depend on the whole repository.
- Tests run against the real repository, so `unique` and existing files still apply. Use inputs that will not exist, such as `example`.

### Template functions

adder provides a small set of deterministic functions alongside Go's [built-in template functions](https://pkg.go.dev/text/template#hdr-Functions). Names follow [Sprout](https://github.com/go-sprout/sprout) where it has an equivalent.

| Function | Example | Result |
| --- | --- | --- |
| `toLower`, `toUpper` | `toUpper "abc"` | `ABC` |
| `toCamelCase` | `toCamelCase "user_id"` | `userId` |
| `toPascalCase` | `toPascalCase "user_id"` | `UserId` |
| `toSnakeCase` | `toSnakeCase "HTTPServer"` | `http_server` |
| `toKebabCase` | `toKebabCase "HTTPServer"` | `http-server` |
| `toConstantCase` | `toConstantCase "HTTPServer"` | `HTTP_SERVER` |
| `toGoCamelCase` | `toGoCamelCase "user_id"` | `userID` |
| `toGoPascalCase` | `toGoPascalCase "user_id"` | `UserID` |
| `fieldValues` | `fieldValues "Package" .Drivers` | the `Package` field of every item |
| `uniq` | `uniq (list)` | values with repeats removed, in first-seen order |
| `sortAlpha` | `sortAlpha (list)` | values sorted alphabetically |
| `groupBy` | `groupBy "Dir" .Handlers` | a list of groups, each with `.Key` and `.Items`, sorted by key |
| `sortBy` | `sortBy "Iota" .Colors` | the items sorted by a string or number field, keeping the order of equal ones |
| `join` | `fieldValues "Name" .Drivers \| join ", "` | `local, s3` |
| `trimPrefix`, `trimSuffix` | `trimPrefix "Handle" .Name` | `Users` for `HandleUsers` |
| `replace` | `replace "-" "_" .Dir` | `go_redis` for `go-redis` |
| `quote` | `quote .Name` | `"s3"`, quoted as Go writes strings |
| `indent`, `nindent` | `nindent 4 .Doc` | every line indented by four spaces, after a newline with `nindent` |
| `plural` | `plural "driver" "drivers" (len .Drivers)` | `driver` for exactly one, `drivers` otherwise |

Functions that Sprout also has take the value last, so they work at the end of a pipeline. adder has no function that works out plurals by itself, since English needs a list of exceptions that would never be finished; write the plural, as in `{{ .Name }}s`, or take it from a directive argument for irregular words.

Case functions split words at separators such as `_`, `-`, and spaces, at lowercase-to-uppercase changes, and at the end of an acronym: `HTTPServer` is `HTTP` and `Server`. The Go variants produce identifiers that follow Go naming style: they keep words already in capitals, such as `BMC`, and capitalize common initialisms such as `ID`, `HTTP`, and `URL`.
